CareerForge AI — Architecture & Decision Guide

Author & © Arpit Sahu · MIT · verified against code, manifests, ADRs & tests · in sync with ARCHITECTURE.md
Audience An engineer who needs to understand, modify, or explain any part of the system — and answer "why was it built this way?" — without reading the source first. Every fact was verified against the code, the pyproject.toml/package.json manifests, the three ADRs, and the test suites.

1 · Mental model

CareerForge AI is a local-first, modular-monolith platform that turns information into verified career evidence: it analyzes a GitHub repository through a multi-stage mission (intake → static analysis → runtime → aggregate → duplicate-check → fix → independent verification → human approval), and separately maintains an evidence-backed skill profile, an industry-pulse feed, artifact assignments, and a public portfolio. The backend is one FastAPI deployable (apps/api, package careerforge_api) that streams a live mission to a Next.js console (apps/web) over Server-Sent Events; each real capability is its own installable package under packages/.

The one sentence that explains most of the design Use the real provider when it's present, a dependency-free fallback when it isn't — so the whole system runs anywhere with just Python + Node, while the wire contract stays identical to the fully-provisioned deployment.

That principle explains the demo runtime that scripts a realistic mission (ADR-0003); embeddings falling back Ollama→hash; the vector store falling back Qdrant-server→in-process :memory:; the sandbox no-op'ing safely without Docker; observability falling back OpenTelemetry→in-memory tracer; and every subsystem being optional behind an interface that reports its live mode in GET /system/health.

7 · Subsystem deep dives

7.1 Mission engine — lifecycle

MissionStore is a process-wide, RLock-guarded registry. append() increments a per-mission monotonic counter, appends to a replay buffer, and folds the event into live state; log/resource events live only in the buffer. MissionSimulator seeds its RNG from sha256(repo_url) — never system entropy — so the same URL always tells the same story and guarantees ≥1 ACCEPTED + ≥1 REJECTED candidate.

stateDiagram-v2
  [*] --> QUEUED
  QUEUED --> PLANNING: ENGINE.run task starts
  PLANNING --> RUNNING: stages execute
  RUNNING --> AWAITING_APPROVAL: a candidate ACCEPTED then non-submittable draft
  RUNNING --> COMPLETED: no candidate accepted
  AWAITING_APPROVAL --> COMPLETED: approve
  AWAITING_APPROVAL --> CANCELLED: reject
  COMPLETED --> [*]
  CANCELLED --> [*]
  • SSE immediately yields a resource snapshot, replays from Last-Event-ID (header or ?lastEventId=), heartbeats every 15 s as an SSE comment, ends once complete and caught-up.
  • ENGINE.run drives the synchronous script() list with its own pacing (0.14 s demo) — not the simulator's async run(); tests drain it with no sleeps via run_mission_sync.
  • The approval endpoint hard-overrides github_write=False; test_approval_never_performs_github_write asserts it.

7.3 RAG pipeline (rag_core)

Fixed order: validate_domain → dense+sparse → RRF (k=60) → rerank → time/version filter → dedupe by (path,symbol) → NO-ANSWER if empty or top score < 0.15 → top-K (8) → build citations → generate claims → verify each claim vs exactly its cited chunks → answered = any supported. Six fixed collections. The time/version filter keeps the newest published_at per (path,symbol) — suppressed when the query asks for history.

7.4 Sandbox (sandbox) — security-critical

Hardening (pure build_run_args)--user 65534:65534, --cap-drop ALL, --security-opt no-new-privileges, --read-only, --tmpfs /tmp:rw,size=256m,noexec, repo bind-mounted ,ro, --memory/--cpus/--pids-limit, --network none (only install stage gets bridge). No host home / SSH / Docker-socket / token mounts, ever.

The policy engine is an allowlist (python/pytest/ruff/mypy/pip/uv/coverage), a denylist (rm, curl, sudo, docker, … anywhere), a shell-metacharacter reject, and source/sh/bash blocked at argv[0]. Deterministic and model-independent so an LLM cannot widen its own permissions.

7.5 GitHub client (github_client) — read-only, token-safe

Read-only is enforced at the transport layer: _ReadOnlyTransport raises ReadOnlyViolation for any non-GET before a byte leaves the process. The token lives in a SecretStr, only ever in the Authorization header; __repr__ shows only URL + authenticated bool; every error path runs through redact(). list_issues excludes PRs; rate-limit is raised only on a genuine 403/429 rate-limit signal.

7.6 Frontend data flow (apps/web)

analyzeRepo → seed Zustand store → useMissionStream opens an EventSource, registers one listener per contract event, dispatch() maps each to a store action; components subscribe with selectors. System health/resources use a separate TanStack Query polling path (5 s), distinct from the SSE mission telemetry. Heavy libs are isolated per screen: React Flow (Command Center), R3F (Skills, ssr:false + WebGL fallback), Monaco (Lab, ssr:false + unified-diff fallback), ECharts (Pulse).

10 · Glossary

  • Mission — one repository-analysis run; the central aggregate.
  • Demo mode — APP_ENV=demo (default); scripted deterministic mission over the real SSE contract; services report "mock".
  • Contract — the fixed JSON/SSE shapes in docs/API_CONTRACT.md, mirrored in schemas.py and lib/types.ts.
  • Degrade gracefully — probe a provider; on absence use a deterministic fallback and log it (Rule 1).
  • Gate / flag — a CAREERFORGE_FLAG_* boolean (default false) guarding a dangerous action.
  • Verifier independence — a verify.* agent is never the fix.* author of the candidate it checks (Rule 3).
  • NO_SUBMISSION — a candidate verdict meaning "don't propose a PR"; always available.
  • RRF — Reciprocal Rank Fusion (k=60) merging dense + BM25 rankings.
  • Preflight — the sandbox's read-only static risk scan; HIGH ⇒ BLOCKED.
  • Last-Event-ID — the SSE cursor (monotonic per mission) enabling exact reconnect/replay.

Known code/doc discrepancies (reported honestly)

Verified, not hidden
  • static_analysis/ast_agents.py's docstring claims pickle.loads/yaml.load/validation-assert detection, but the code detects only bare-except:, eval/exec, shell=True, verify=False.
